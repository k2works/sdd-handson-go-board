    GoBoard Bolt 5 計画（引き分けとリリース）¶

    Bolt ゴール¶

    盤がすべて埋まったとき（R8）と、手番のプレイヤーが置けるマスが 1 つもなくなったとき（R10）に、引き分けでゲームを終える。画面に「引き分け」を表示し、v0.1.0 として最初の手から勝敗（または引き分け）まで通しで遊べるようにする。これで、ルールにない振る舞いが残っていないかが分かる。

    対象¶

    項目 内容
    Unit U3 勝敗判定・U4 Web 画面
    ストーリー S08・S12、S10（引き分け）
    フィーチャーファイル result/s08_draw_full_board.feature・result/s12_draw_no_placeable_cell.feature・screen/s10_show_result.feature
    承認ゲート 自律実行（テストが失敗したときだけ止まる）。Bolt の完了は実装・テスト・CI・ドキュメントまでとし、プロダクトオーナーの確認は v0.1.0 のリリース判断（タグ付け）として Bolt の後に行う

    設計の方針¶

    • 勝負の状態に引き分けを加える：Outcome に draw を加える。Game.play は、置いたあとに勝ちがなければ、盤が埋まったか（R8）、次の手番のプレイヤーが置けるマスがないか（R10）を判定する。置けるかどうかは、R9 まで含めて Game.play と同じ判定を使う。
    • 再開時も同じ判定をする：Game.resume は、勝ち → 盤の埋まり → 手番のプレイヤーが置けるマスの有無の順に判定する。
    • 盤面のフィクスチャ：探索スクリプトで作り、手順どおりに打ち進めて検証した。
    • 盤が埋まって引き分け（FULL_BOARD_DRAW）：犬 113・猫 112 で、どこにも同じ種類の 3 つ以上の連続がない。どの途中の盤も連続は 2 以下なので、勝ちにも R9 にも当たらず、最初の手から画面のクリックで到達できる。最後に犬が 8 行 8 列に置く。
    • 置けるマスがなくなって引き分け（NO_PLACEABLE_DRAW）：上の盤から 5 行 7 列と 1 行 3 列を空けた盤。手番は猫。猫が 1 行 3 列に置くと、犬が置けるのは 5 行 7 列だけになり、そこは 4 方向にちょうど 3 つの並びができるため R9 で置けない。この盤は駒数の制約から画面のクリックでは到達しにくいため、Game.resume で用意してルールに対して確かめる（案 A）。
    • 受け入れテストの盤の準備：盤が埋まる引き分けは、画面のクリックで最初の手から準備する。225 手のクリックを速く行うため、準備のステップではブラウザ内でボタンを順にクリックし、確かめる操作（最後の 1 手）は Playwright でクリックする。
    • 引き分けの表示の確認（S12）：画面で到達しにくいため、画面が使う表示の関数（statusMessage）で、ルールに対して「引き分け」と表示されることを確かめる。盤が埋まる引き分けの表示（S10）は画面で確かめる。
    • リリース：apps/goboard/package.json のバージョンを 0.1.0 にし、apps/goboard/CHANGELOG.md を作る。Git のタグ付けは外部に公開する操作のため、プロダクトオーナーの判断を待つ。
    • 仮定 A3：もう 1 局続けて遊ぶ機能は v0.1.0 に含めない（仮定のとおり、何も作らない）。

    ステップ¶

    • 1. 盤が埋まる引き分け（R8）と、置けるマスがなくなる引き分け（R10）の単体テストを書き、Game に draw を加える（S08・S12）
    • 2. 画面のテストを書き、「引き分け」の表示を実装する（S10）
    • 3. S08・S12・S10（引き分け）のシナリオから @wip を外し、ステップ定義を実装する
    • 4. バージョンを 0.1.0 にし、CHANGELOG を作る
    • 5. 受入条件のチェックボックス・リリース計画の進捗・本計画の結果を更新し、CI の成功を確かめる

    完了条件¶

    • すべてのシナリオから @wip がなくなり、npm run test:acceptance が成功する
    • apps/goboard/ で npm run typecheck・npm test・npm run build が成功する
    • push したコミットで GitHub Actions の GoBoard CI が成功している
    • src/game/ が React や DOM に依存していない
    • ルール定義にない振る舞いを加えていない

    項目 結果

    単体テスト 79 件すべて成功（ルール 63 件、画面 16 件）
    型チェック・ビルド npm run typecheck・npm run build 成功
    CI GoBoard CI（コミット f96b27a、実行 36233125034）が成功

    リリース apps/goboard/package.json を 0.1.0 にし、apps/goboard/CHANGELOG.md を作成。Git のタグ付けはプロダクトオーナーの判断を待つ

    仮説の検証¶

    • 最初から最後まで遊んだとき、ルールにない振る舞いが残っていないか：残っていない。盤が埋まる引き分けの受け入れテストで、最初の手から 225 手を画面のクリックで打ち切り、途中で勝ちにも R9 にも当たらず、最後に「引き分け」と表示されることを確かめた。すべての受入条件（S01〜S12）がシナリオとして成功し、画面にあるのは盤・手番または結果・置けない理由だけで、ルール定義にない操作（パス、やり直し、もう 1 局など）はない。

    学び¶

    • 「最終形のどこにも 3 つ以上の連続がない」盤面は、そのどの途中の盤でも勝ちにも R9 にも当たらない。この性質を使うと、画面のクリックで最初の手から到達できる盤面を、探索で安全に作れた。
    • 「置けるマスがなくなる」盤面は、犬と猫の駒の数の制約で、元の模様からの入れ替えだけでは作れなかった（1 つ入れ替えると必ず 3 つの連続ができる）。探索に時間をかけるより、Game.resume で用意してルールに対して確かめる方式（案 A）に切り替えた。
    • 225 手のクリックを、テストの準備で速く行うには工夫が要った。単体テストではボタンを 1 回だけ集めて使い回し（39 秒 → 1.3 秒）、受け入れテストではブラウザ内で 1 手ごとに画面の更新を待ちながらクリックした。
    • 置けるかどうかの判定（盤の外・駒のあるマス・R9）を 1 つの関数にまとめたことで、play と R10 の判定が同じ基準を使うことを構造で保証できた。

    未確認のこと¶

    • 他のブラウザ（Firefox・Safari）での見た目（リスク K1）。この開発環境には Chromium しかなく、確かめていない。プロダクトオーナーのリリース判断の前に、手元のブラウザで確かめてもらう。
