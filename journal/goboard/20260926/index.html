    2026-09-26 開発ジャーナル¶

    空のリポジトリの状態確認から始め、プロダクトオーナーが説明したルールだけを正解とする 2 人対戦のボードゲーム「GoBoard」を、ルール定義 → ストーリー → Unit と Bolt の計画 → 5 つの Bolt の TDD → v0.1.0 のリリースまで、1 日（約 2 時間）で進めた。途中で Go の CLI から TypeScript・React の Web アプリへの変更、ルール R9・R10 の追加、BDD（Cucumber と Playwright）の導入が入り、そのたびに計画と成果物を直してから先に進んだ。リリースのあとは、実装済みのコードからドメインモデル・UI 設計・アーキテクチャ設計を書き起こし、設計整合性の横断検証で見つかったずれを直した。

    ハイライト¶

    • ルールをプロダクトオーナーとの対話で R1〜R10 に確定し、既存ゲームの一般的なルールで空白を埋めないことを CLAUDE.md のガードレールにした。ルール定義はプロダクトオーナーが検証した
    • Go の CLI から TypeScript・React の Web アプリに切り替え（ADR 0001）、受入条件を日本語 Gherkin にして Cucumber と Playwright で検証する形にした（ADR 0002）
    • 5 つの Bolt ですべてのストーリー S01〜S12 を完了した。受け入れテスト 60 シナリオ・単体テスト 79 件・GoBoard CI がすべて成功し、各 Bolt で実装を意図的に壊してテストが失敗することを確かめた
    • 受け入れテストが開発環境の中でしか通らない状態で「成功」と報告していたことを、プロダクトオーナーの指摘で知った。Playwright の版を固定し、GitHub Actions の CI を追加して、npm ci からの実行と CI の成功を完了条件にした
    • タグ v0.1.0 を付けてリリースした。タグの push はセッションの制限でできず、プロダクトオーナーが GitHub に作成した
    • リリース後に、コードから設計ドキュメント 3 本（ドメインモデル・UI 設計・アーキテクチャ設計）を書き起こし、横断検証で見つかった 9 件のずれのうち 5 件を直した。残りはプロダクトオーナーの判断待ち

    計画フェーズ Skill 実行の時系列¶

    1. orchestrating-project --status — 空のプロジェクトの状態確認¶

    引数は —stataus（全角ダッシュと綴りの誤り）だったが、--status と解釈した。要件・計画・コード・Issue・PR のどれもなく、apps/ は空だった。そのため「リリース計画の前に Intent と要件が必要」と報告し、orchestrating-analysis から始めることを提案した。

    2. Intent とルールの確定 — 対話によるルール定義¶

    プロダクトオーナーは「5 目並べ」などの一般名称に頼らず、自分の説明だけを正解にしたいと明言した。説明は「二人対戦。オブジェクトを先に盤上に 5 つ並べた方が勝ち」の 1 文だけだった。

    版 内容 判断の経緯
    v0.1 R1〜R3（説明の 1 文） 未決の 12 項目を質問として並べた。答えの見当は付けず、観点だけを示した
    v0.2 12 項目すべてに AI の案 「任せる」を受け、「説明が短い・例外がない・最初の Bolt で動くものを早く作れる」の 3 つを基準に案を作った。6 つ以上も勝ちにしたのは、例外を作らないため
    v0.3 駒を黒・白から犬・猫に プロダクトオーナーの指定。先手と表示（絵文字の幅）を新たな論点として提示
    v0.4 用語を「石」から「駒」に プロダクトオーナーの指定。コード上の名前（Piece・Board・Cell）もここで決めた
    v1.0 承認 docs/requirements/goboard/ルール定義.md に保存。出典（プロダクトオーナー / AI の案を承認）を列で区別した

    最初は docs/requirements/ の直下に置いたが、ドキュメント構成ガイドの「要件定義以降はプロジェクト別サブディレクトリ」に反していたため、プロジェクト識別子 goboard を決めて移した。

    3. analyzing-usecases 相当・planning-releases 相当 — ストーリーと Unit・Bolt 計画（/goal ３完了まで）¶

    成果物 内容
    docs/requirements/goboard/ユーザーストーリー.md S01〜S10（のちに S12 まで）。受入条件を Given/When/Then にし、ルール番号へのトレーサビリティ表を付けた
    docs/development/goboard/release_plan.md Unit U1〜U4、依存関係、実装エントロピー評価、Bolt 計画、リスク台帳、未確認の仮定
    docs/development/goboard/bolt_1_plan.md ウォーキングスケルトンのステップ計画
    CLAUDE.md 「GoBoard のルールはルール定義だけが正解」をコア原則に追加

    4. Web アプリへの変更 — ADR 0001¶

    Bolt 1 のステップ 1（Go モジュールの骨組み）の承認ゲートで、プロダクトオーナーから「UI まで一貫した Web アプリにしたいので TypeScript に」という指示が来た。対戦形態（同じブラウザで交互か、オンラインか）と UI フレームワークは、AskUserQuestion で選んでもらった（同じブラウザ・React + Vite）。Go の骨組みを削除し、ストーリー（S09 を座標入力からクリックに）・計画・ルール定義の「遊び方」を直してから、骨組みを作り直した。

    開発フェーズ Skill 実行の時系列¶

    5. Bolt 1（ウォーキングスケルトン）— 各ステップで承認ゲート（/goal Bolt1）¶

    盤（Board、1 始まりの位置、イミュータブル）→ 置く（place）→ 盤の画面（role="grid"・各マスは「8 行 8 列 空き」という読み上げ名のボタン）→ クリックで犬を置く、の順に Red → Green → Refactor を回した。Playwright で撮影し、225 マスが 36 × 36 px でそろうことをプロダクトオーナーに確認してもらった。tsc で CSS の import を解決するため、tsconfig に vite/client の型を足した。

    6. ルールの追加 R9・R10¶

    「ちょうど 3 つの並びが同時に 2 か所以上できるならそこに置けない」というルールが追加された。並びの向き、ちょうど 3 つの意味、数える並びの範囲、ふさがれた端、対象、R7 との順番、置けないときの扱い、置けるマスがなくなった場合の 8 論点に案を付けて提示し、承認を得た。8 つ目の論点は R10（置けるマスがなければ引き分け）として独立させた。提示した図の例が不正確だった（★ の縦に犬がなかった）ので、受入条件では座標を明示し、1 件ずつ検算した。

    7. BDD の導入 — ADR 0002¶

    「BDD 導入ガイドに従って Cucumber を設定し、Playwright で受け入れテストを。ストーリーを Gherkin に変換してから」という指示を受けた。

    • S01〜S12 を 1 ストーリー 1 ファイルの日本語 Gherkin にし、機能領域ごとのフォルダ（start・placement・turn・result・screen）に置いた。タグ（@S01・@R2・@U1・@wip）は features/tags.md に一覧化した
    • tsx は --loader では読み込めず、node --import tsx で Cucumber を起動する形にした
    • 設定ファイルの tags: 'not @wip' とコマンドラインの --tags @wip は AND になり、0 シナリオになった。profile を分けて解決した
    • 犬の絵文字を一時的に別のものに変えて、受け入れテストが失敗することを確かめた（以降、各 Bolt で同じ確認をした）

    8. Bolt 2〜5 — 自律実行（/goal Bolt2〜/goal Bolt5）¶

    Bolt 内容 判断・ハマったポイント
    2 置けない場所と手番（Game を追加） リファクタリング中に、盤の外の pieceAt(1 行 16 列) が隣の行のマスを返す不具合を見つけ、テストで再現してから直した。受け入れテストの盤の準備は画面のクリックで行い、手番を進める相手の駒は最下段に置いた
    3 勝ち（runLength・outcome・resume） 「224 マスが埋まり最後の 1 マスで勝つ」盤面を探索スクリプトで作り、総当たりで検証してからフィクスチャにした
    4 R9 S11 は「特に書いていないマスは空いている」盤が必要で、画面のクリックでは作れない。案 A（Game.resume でルールに対して検証）と案 B（URL で盤面を渡す）から A を選んだ。フィーチャーファイル名に既存ゲームの用語（double three）が入っていたのを、ルール定義の言葉に改名した
    5 引き分け（R8・R10）と v0.1.0 「最終形のどこにも 3 つ以上の連続がない」盤面は、途中のどの盤でも勝ちにも R9 にも当たらないので、画面のクリックで最初から到達できる。置けるマスがなくなる盤面は、駒数の制約から模様の入れ替えでは作れなかった（1 つ替えると必ず 3 つの連続ができる）。9 分探索して収束しなかったので、案 A に切り替えた

    9. 受け入れテストの失敗の指摘と CI（operating-cicd 相当）¶

    Bolt 3 のあと、プロダクトオーナーから「受け入れテスト失敗してるよ！！！」と指摘された。環境変数なしで実行すると再現した。原因は、最新の Playwright 1.63 を入れたのに、開発環境には 1.56 系用の Chromium（revision 1194）しかなかったことだった。環境変数でブラウザを指定して実行していたため、そのままでは動かないことを見落として「成功」と報告していた。

    • Playwright を 1.56.1 に固定（^ なし）した
    • npm run test:acceptance:setup と、ブラウザを起動できないときに実行すべきコマンドを案内するエラーを追加した
    • node_modules を消して npm ci から検証し直した
    • .github/workflows/goboard-ci.yml を追加した（型チェック → 単体テスト → ビルド → Chromium のインストール → 受け入れテスト）。最初の実行から成功した
    • Bolt の完了条件に「push したコミットで CI が成功している」を加えた

    10. developing-release・creating-release-report — v0.1.0¶

    品質ゲート（作業ツリー・型チェック・テスト・ビルド・受け入れテスト・CI）をすべて通し、注釈付きタグを作った。ところが、タグの push はセッションの Git の中継に 6 回とも切断された。GitHub のツール（MCP）にもタグを作る操作はなかった。プロダクトオーナーにタグの作成を依頼し、バックグラウンドで 1 分ごとに GitHub を確認して、タグができたことを検知した。プロダクトオーナーは報告書のタグの記述を直すコミット（97ddd23）を足してタグを付けていたので、ブランチをそこまで早送りしてそろえた。

    設計フェーズ（ブラウンフィールド）Skill 実行の時系列¶

    11. creating-journal — コミットの中断と退避¶

    このジャーナルの最初の版を書いてコミットしようとしたところで、プロダクトオーナーがコミットを止め、analyzing-domain-model に切り替えた。止められた操作を確認なしにやり直すことはせず、ジャーナルの変更は git stash に退避して作業ツリーをきれいに保った（Stop フックが未コミットの変更を拒むため）。そのあとプロダクトオーナーの「ジャーナル」の指示で戻し、本節以降を追記した。

    12. analyzing-domain-model — コードからの書き起こし¶

    実装とテストが先にあるので、AI-DLC のブラウンフィールドの進め方で、src/game/ からモデルを書き起こした。成果物は docs/design/goboard/domain-model.md。

    内容 要点
    境界付けられたコンテキスト 対局ルール（中核）と画面（一般または補完）の 2 つ
    集約 対局（Game）が集約ルート。不変条件 I1〜I8 を、どのコードで守っているかと対応づけた
    設計上の判断 対局は識別子を持たない、位置は生成時に検証しない（S04 の「盤の外」を値で表すため）、R9 は盤ではなく対局で判定する、など 6 項目

    ハマったのは、ジャーナルの作業でステージしていた docs/journal/.gitkeep の削除が、ドメインモデルのコミットに紛れ込んだこと。push 済みだったので履歴は書き換えず、戻すコミットを足した。git add <パス> で選んでも、すでにステージ済みの変更はコミットに入る。

    13. analyzing-ui-design — 1 画面の状態遷移¶

    src/ui/ から docs/design/goboard/ui-design.md を書き起こした。画面は 1 つで、状態（犬の手番・猫の手番・勝ち・引き分け）によって表示が変わる。書き起こしの中で、role="grid" なのに矢印キーで移動できない（Tab で 225 マス）、もう 1 局遊ぶには再読み込みが要る、狭い画面で盤がはみ出す、といった改善候補 U1〜U4 に気づいた。どれも操作やルールに関わるので、実装はせずに判断を仰いだ。

    14. validating-design — 横断検証と修正¶

    スキルは開発戦略とイテレーション計画を前提にしているが、GoBoard にはどちらもない。そこで「リリース計画 ↔ Bolt 計画」「計画・要件 ↔ 設計ドキュメント」「Bolt 計画どうし」に読み替えて検証し、9 件のずれを見つけた。

    対応 ずれ
    すぐ直した（A1・B2・B5・B6） 完了条件に人の確認が残っていた、U1 の責務に R9 が入っていた、Bolt 1 の説明が「座標入力」のまま、ストーリーの説明が「S01〜S10・R1〜R8」のまま
    判断を仰いで直した（B1・B7） Bolt 計画に設計図がない、アーキテクチャ設計のドキュメントがない
    判断待ち（B3・B4） ルール定義の用語集のコード上の名前（Dog / Cat・GoBoard）がコードと合わない、用語集が 2 か所に分かれている

    スキルは「指示があるまでコミットしない」と定めているので、検証の報告だけをして、修正はプロダクトオーナーの Y を待ってから行った。

    15. analyzing-architecture — 1 本にまとめたアーキテクチャ設計（B7）¶

    スキルは、バックエンド・フロントエンド・インフラの 3 ファイルを想定している。GoBoard にはサーバーもデプロイ先もないので、docs/design/goboard/architecture.md の 1 本にまとめ、ガイドの選択フローに当てはめて「ドメインモデル ＋ 出力ポートのない形」「SPA ＋ useState」を評価した。

    調べる中で、docker-publish.yml がすべてのタグの push で動く設定だと分かった。v0.1.0 のタグで、GoBoard ではなくリポジトリの開発環境の Docker イメージが GitHub Container Registry に v0.1.0 として公開されていた（F2）。外部に公開される設定なので、配信先（F1）・Chromium 以外のブラウザ（F3）とあわせて判断を仰いだ。

    16. B1 — Bolt 計画に範囲を絞った設計図¶

    完了済みの Bolt 1〜5 の計画に、その Bolt で扱った範囲だけのドメインモデル図・状態遷移図・画面遷移図を 14 図足した。ER 図はデータベースがないので省略し、Bolt 1 の状態遷移図も状態を持つ対局がないので省略した。

    PlantUML の描画環境はなかった。Maven からの jar の取得は 429 で断られたが、npm の node-plantuml-latest に vendor/plantuml.jar が同梱されていたので、それで -checkonly を実行した。壊した図で失敗することを確かめたうえで、設計ドキュメントを含む 26 図すべてが通ることを確認した。

    ハマったことが 2 つあった。

    • python の文字列で '\\n' と書いて、リリース計画の改訂履歴に改行ではなく「\n」という文字を入れてしまい、表も崩した。直すのに 2 回コミットした
    • スクラッチパッドの古いファイルを rm で消そうとして、安全チェックに止められた。消さずに別のディレクトリを作って進めた

    17. operating-docs --update — 索引とナビの同期¶

    docs/index.md に GoBoard の主なドキュメントへの入口を足し、要件・設計・運用の索引の「状況：未作成」だけの標準表を「GoBoard」の列に変えて、作成済みの文書へのリンクと対象外の理由を書いた。開発の索引は、AI-DLC に合わせてイテレーションと SP の表を Bolt とストーリーの表にした。ナビの 87 項目が実在するファイルを指すことを確かめた。

    学び¶

    • 「成功」は、他の人の環境で再現できる形で確かめてから報告する。 環境変数や手元にしかないブラウザで通ったテストは、成功の証拠にならない。npm ci からの実行と CI を、完了条件の側に入れておく
    • ルールの空白は質問で埋め、案を出すときは選んだ基準を添える。 「任せる」と言われたときも、案と理由（例外を作らない・説明が短い）を示して承認を得ると、あとで「なぜ 6 つ以上も勝ちなのか」を説明できる
    • ガードレールは、コードだけでなくファイル名・テスト名にも効かせる。 既存ゲームの用語は、気づかないうちにファイル名に紛れ込んだ
    • 盤の不変条件と、置くときのルールは分ける。 R9 を Board.place で判定すると、テストの盤面すら作れなくなる。不変条件（盤の外・駒のあるマス）は盤が守り、手のルール（R9・R10）は対局が判定する
    • 画面から用意できない状態は、ルールに対して直接確かめる。 本番コードにテスト用の入口を作るより、画面の確認は最小限にして、ドメインに対する受け入れテストで網羅する方が単純だった
    • 手で作ると誤りやすいテストの盤面は、探索と総当たりの検証で作る。 その際、単調性（最終形に 3 つ以上の連続がなければ、どの途中でもない）のような性質を使うと、探索の範囲を狭められる。収束しない探索に時間をかけすぎない（9 分で切り替えた）
    • 人の確認を /goal の完了条件に入れると、確認を待つ間に Stop フックが同じ応答を繰り返す。 目標は AI が自力で満たせる条件（実装・テスト・CI）にし、人の確認は目標の外で行う
    • pkill -f <名前> は、同じ名前を含む自分のシェルまで止める。 止める対象はプロセス ID で指定する
    • 実装が先にあるときの設計ドキュメントは、コードから書き起こし、ずれを「設計上の判断」として明記する。 書き起こす過程で、role="grid" と矢印キーの不一致や、タグで別のイメージが公開される設定のような、実装だけ見ていると気づかない問題が見つかった
    • スキルの前提（開発戦略・イテレーション計画・3 本のアーキテクチャ文書）がプロジェクトと合わないときは、読み替えを宣言してから使う。 前提のないまま型どおりに当てはめると、空の文書が増えるだけになる
    • ステージ済みの変更は、パスを選んで git add してもコミットに入る。 別の作業の変更が混ざっているときは、先に git status でステージの状態を確かめる
    • タグは、そのリポジトリのほかのワークフローも起動する。 タグを付ける前に、on: push: tags を持つワークフローを確かめる
